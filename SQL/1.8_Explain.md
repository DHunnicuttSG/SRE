# EXPLAIN: Reading a SQL Execution Plan

## What Is EXPLAIN?

**`EXPLAIN`** shows how a database's query optimizer plans to execute a SQL statement.
It helps you answer questions such as:

- Which table will be read first?
- Will the database use an index?
- How many rows might the database examine?
- In what order will joins be performed?
- How could a slow query be improved?

`EXPLAIN` describes a **plan**. It does not execute the query or modify the data.

In MySQL, it is commonly used before a `SELECT` statement:

```sql
EXPLAIN
SELECT *
FROM customers
WHERE email = 'ada@example.com';
```

Other database systems use `EXPLAIN` in similar ways. PostgreSQL, for example, uses `EXPLAIN` and `EXPLAIN ANALYZE`.
MySQL supports `EXPLAIN ANALYZE` in recent versions.

---

## Why Use EXPLAIN?

A query can produce the correct result but still perform poorly.
For example, a query that searches a million-row table might read the entire table instead of locating matching rows through an index.

An execution plan helps you find:

- Missing indexes
- Inefficient join order
- Full table scans
- Large intermediate result sets
- Unnecessary sorting or temporary tables
- Rows that are examined but not returned

## Example Tables

Suppose we have two tables:

```sql
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,
    total DECIMAL(10, 2) NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

Create a few example indexes:

```sql
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_order_date ON orders(order_date);
```

## Basic EXPLAIN Output

Run a simple lookup:

```sql
EXPLAIN
SELECT name, email
FROM customers
WHERE customer_id = 42;
```

A MySQL result might look similar to this:

| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
| -- | ----------- | ----- | ---------- | ---- | ------------- | --- | ------- | --- | ---- | -------- | ----- |
| 1 | SIMPLE | customers | NULL | const | PRIMARY | PRIMARY | 4 | const | 1 | 100.00 | NULL |

Do not memorize the exact values. Read the columns as evidence about how the query may execute.

---

## Important EXPLAIN Columns

### `table`

The table or intermediate result being processed.

### `type`

Describes how rows are found. It is one of the most useful columns.

| Type | Meaning | Performance Note |
| ---- | ------- | ---------------- |
| `system` | Table has one row or is known to have no rows | Excellent |
| `const` | At most one matching row, usually found using a primary key or unique key | Excellent |
| `eq_ref` | One row is read from this table for each joined row | Excellent |
| `ref` | Multiple rows may match a non-unique index | Good |
| `range` | Rows are retrieved from an index over a range | Good |
| `index` | The entire index is scanned | Often less efficient |
| `ALL` | The entire table is scanned | Usually inspect for improvement |

The exact interpretation depends on table size and the rest of the query.
For a very small table, a full table scan may be reasonable.

### `possible_keys`

Indexes the optimizer considered useful for the query.

If this column is `NULL`, no relevant index was available.

### `key`

The index the optimizer chose to use.

If this column is `NULL`, the optimizer did not choose an index for this step.

### `key_len`

The number of bytes used from the chosen index.
It can help identify whether a composite index is being used only partially.

### `ref`

The column or constant compared with the index key.

### `rows`

An estimate of the number of rows MySQL expects to examine.

This is an estimate, not an exact count. Lower estimates are generally better, but data distribution and query complexity also matter.

### `filtered`

The estimated percentage of rows that remain after table conditions are applied.

For example, `filtered = 10.00` means only an estimated 10% of examined rows pass the remaining conditions.

### `Extra`

Additional execution details.

| Extra Value | Meaning | Consider |
| ----------- | ------- | -------- |
| `Using index` | The index contains all needed columns | Often efficient |
| `Using where` | Rows are filtered after retrieval | Normal, not automatically bad |
| `Using temporary` | A temporary table is created | May be slow for large data sets |
| `Using filesort` | Rows are sorted outside an index | Investigate if the result is large |
| `Range checked for each record` | Join filtering depends on row-by-row index checks | Can indicate a join optimization opportunity |
| `Impossible WHERE` | The condition cannot match any row | Review the condition |

## Identifying an Index Use

This query searches a customer by an indexed primary key:

```sql
EXPLAIN
SELECT name
FROM customers
WHERE customer_id = 42;
```

The plan may show:

- `type = const`
- `possible_keys = PRIMARY`
- `key = PRIMARY`

This is a strong, direct lookup.

By contrast:

```sql
EXPLAIN
SELECT name
FROM customers
WHERE name = 'Ada Lovelace';
```

If no index exists on `name`, the plan may show:

- `type = ALL`
- `key = NULL`

This means the database may need to scan the table.
An index may improve repeated searches, but not every table scan should automatically be indexed.

## EXPLAIN for a Join

When joining tables, read the plan from top to bottom:

```sql
EXPLAIN
SELECT c.name, o.order_id, o.order_date
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id = 42;
```

What to look for:

1. Is the customer located efficiently using `PRIMARY`?
2. Is `idx_orders_customer_id` used for the join?
3. Are many orders expected for each customer?
4. Is the join order logical?

A likely efficient plan would locate the customer directly and use the indexed `customer_id` column in `orders`.
An index on a foreign key is especially important when the table is joined or filtered by that foreign key.

## Range Searches and Sorting

EXPLAIN can reveal range searches:

```sql
EXPLAIN
SELECT order_id, customer_id, total
FROM orders
WHERE order_date >= '2025-01-01'
  AND order_date < '2025-04-01';
```

If `idx_orders_order_date` is used, `type` may be `range`.

Sorting can require additional work:

```sql
EXPLAIN
SELECT order_id, order_date, total
FROM orders
ORDER BY order_date;
```

If the plan shows `Using filesort`, the database may need to sort the result separately.
An index on `order_date` may provide the required order for a query, but it must match the query shape and should be added only after considering read and write costs.

---

## Composite Indexes

A composite index contains multiple columns:

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

This index can help queries that filter or join on `customer_id`, and it can provide the desired order within each customer's rows.

It may help:

```sql
SELECT order_id, order_date, total
FROM orders
WHERE customer_id = 42
  AND order_date >= '2025-01-01'
ORDER BY order_date;
```

It does not replace an index on `order_date` for every query.
For example, a query that searches only by `order_date` cannot always use `customer_id` as its first part of the composite index efficiently.

This follows the **leftmost-prefix rule**:

> A composite index is most useful when a query uses a prefix of the index, beginning with its first column.

---

## EXPLAIN FORMAT=JSON

For a more detailed plan, MySQL can format the plan as JSON:

```sql
EXPLAIN FORMAT=JSON
SELECT c.name, o.order_id
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id = 42;
```

JSON output contains additional details such as estimated costs and nested loop structure.

Use the regular table format for quick checks and JSON for deeper investigation.

---

## EXPLAIN ANALYZE

`EXPLAIN ANALYZE` runs the query and reports actual execution information.

```sql
EXPLAIN ANALYZE
SELECT c.name, o.order_id
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
WHERE c.customer_id = 42;
```

It may show:

- Actual row counts
- Actual execution time
- Estimated versus actual results
- Time spent in each step

Be careful: `EXPLAIN ANALYZE` actually executes the statement.
Do not use it with statements that change data unless you fully understand the result.
Only use `EXPLAIN ANALYZE` when supported by the database version.

---

## EXPLAIN Versus Executable Statements

`EXPLAIN` is most often used with `SELECT`, but it may also support statements such as:

```sql
EXPLAIN INSERT INTO ...;
EXPLAIN UPDATE ...;
EXPLAIN DELETE FROM ...;
```

Support varies by database.
These statements describe the plan but do not insert, update, or delete data in MySQL.

Other database systems may provide `DESCRIBE` or `\d` for table structure rather than query plans.
Do not confuse table description commands with `EXPLAIN`.

## Optimization Workflow

Use this repeatable process:

1. **Measure or reproduce the performance problem.**
2. **Run `EXPLAIN` on the original query.**
3. **Identify expensive operations**
   - Full scans
   - Large estimated row counts
   - Temporary tables
   - Filesorts
   - Inefficient joins
4. **Check indexes and data distribution.**
5. **Make one focused change.**
   - Add or change an index
   - Rewrite the predicate
   - Select only required columns
   - Change join order or structure
6. **Run `EXPLAIN` again.**
7. **Measure actual performance.**

Optimization should be evidence-based. The optimizer may ignore an index if it estimates that another access path is faster.

## Common Misunderstandings

### “type = ALL means the query is bad”

Not necessarily.
A small table or a query that needs most of the table may legitimately use a full table scan.
The important question is whether the scan is reasonable for the data size and workload.

### “A smaller rows value is always better”

The `rows` column is an estimate.
The real value may differ after the query executes.

### “Adding more indexes always makes queries faster”

Indexes use storage and can slow inserts, updates, and deletes.
Create indexes for recurring, measurable workloads rather than adding every possible index.

### “EXPLAIN always executes the query”

Standard `EXPLAIN` does not execute or modify data.
`EXPLAIN ANALYZE` is an exception because it executes the statement to collect runtime measurements.

### “The best plan is always the plan with no filesort”

Sorting a few rows is not normally a problem.
Investigate `Using filesort` when it occurs on large data sets or frequently run queries.

## Practice Queries

Use this table for the following exercises:

```sql
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    category_id INT NOT NULL,
    name VARCHAR(150) NOT NULL,
    price DECIMAL(10, 2) NOT NULL
);
```

### Exercise 1: Primary Key Lookup

Run:

```sql
EXPLAIN
SELECT name, price
FROM products
WHERE product_id = 100;
```

Identify:

- `type`
- `possible_keys`
- `key`
- `rows`

Is this an efficient lookup? Why?

### Exercise 2: Unindexed Column

Run:

```sql
EXPLAIN
SELECT product_id, name
FROM products
WHERE name = 'Keyboard';
```

Record:

- `type`
- `key`
- `rows`
- `Extra`

Would an index on `name` be appropriate in a high-volume system?
Explain both the benefit and the cost.

### Exercise 3: Range Predicate

Add an index:

```sql
CREATE INDEX idx_products_price ON products(price);
```

Then run:

```sql
EXPLAIN
SELECT product_id, name
FROM products
WHERE price BETWEEN 10 AND 50;
```

What access type is used?
Did MySQL choose the new index?

### Exercise 4: Composite Index

Create:

```sql
CREATE INDEX idx_category_price
ON products(category_id, price);
```

Compare these plans:

```sql
EXPLAIN
SELECT product_id
FROM products
WHERE category_id = 3;

EXPLAIN
SELECT product_id
FROM products
WHERE price = 25;

EXPLAIN
SELECT product_id
FROM products
WHERE category_id = 3
  AND price >= 10
  AND price <= 50;
```

Which query can use the composite index most effectively?
Why might the middle query not use it as efficiently?

### Exercise 5: Sorting

Compare:

```sql
EXPLAIN
SELECT product_id, name
FROM products
ORDER BY name;
```

with:

```sql
CREATE INDEX idx_products_name ON products(name);

EXPLAIN
SELECT product_id, name
FROM products
ORDER BY name;
```

Did `Using filesort` disappear?
If not, why might that happen?

## Summary

| Plan Detail | Why It Matters |
| ----------- | -------------- |
| `type` | Shows how rows are located |
| `possible_keys` | Lists indexes the optimizer considered |
| `key` | Shows the index selected |
| `rows` | Estimates how many rows may be examined |
| `filtered` | Estimates the percentage remaining after filtering |
| `Extra: Using index` | Needed data may come entirely from the index |
| `Extra: Using temporary` | The query may create a temporary result set |
| `Extra: Using filesort` | Results may require separate sorting |
| `EXPLAIN FORMAT=JSON` | Provides more detailed plan information |
| `EXPLAIN ANALYZE` | Runs the query and reports actual execution details |

The key skill is not merely finding the word `ALL` or `Using index`.
It is connecting the plan to the query, table size, indexes, join structure, and workload.
