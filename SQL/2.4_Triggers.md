# MySQL Triggers

## What Is a Trigger?

A **trigger** is a stored database program that MySQL executes automatically when a specified table event occurs. Applications do not call a trigger directly.

Triggers can help with:

- Recording changes in an audit table
- Validating or normalizing values before they are stored
- Maintaining a related value when a row changes

Triggers should be used deliberately. Because they execute automatically, their side effects may not be visible in the SQL statement that caused them.

The examples in this guide use MySQL 8.0.

---

## Trigger Timing and Events

A MySQL trigger is associated with one table, one event, and one timing:

| Timing | Event | When It Runs |
| ------ | ----- | ------------ |
| `BEFORE` | `INSERT` | Before each inserted row is written |
| `AFTER` | `INSERT` | After each inserted row is written |
| `BEFORE` | `UPDATE` | Before each updated row is written |
| `AFTER` | `UPDATE` | After each updated row is written |
| `BEFORE` | `DELETE` | Before each deleted row is removed |
| `AFTER` | `DELETE` | After each deleted row is removed |

MySQL triggers are **row-level**: the trigger body runs once for each row affected, not once for the whole statement.

---

## Basic Trigger Syntax

```sql
DELIMITER //

CREATE TRIGGER trigger_name
BEFORE INSERT ON table_name
FOR EACH ROW
BEGIN
    -- Trigger statements
END //

DELIMITER ;
```

As with stored procedures, the delimiter change is a command for the SQL client. It lets the client send the full trigger definition, including internal semicolons, to the server.

---

## The `NEW` and `OLD` Row Values

Triggers use `NEW` and `OLD` to refer to the row values involved in the event.

| Event | `NEW` Available? | `OLD` Available? |
| ----- | ---------------- | ---------------- |
| `INSERT` | Yes | No |
| `UPDATE` | Yes | Yes |
| `DELETE` | No | Yes |

In a `BEFORE INSERT` or `BEFORE UPDATE` trigger, a permitted `NEW` column can be assigned a value:

```sql
SET NEW.EmailAddress = LOWER(TRIM(NEW.EmailAddress));
```

`OLD` is read-only. `NEW` values cannot be changed in an `AFTER` trigger because the row has already been written.

## Example: Normalize a Value Before Insert

Suppose a practice table stores email addresses:

```sql
CREATE TABLE TriggerPracticeContact (
    ContactId INT AUTO_INCREMENT PRIMARY KEY,
    EmailAddress VARCHAR(255) NOT NULL
);
```

A `BEFORE INSERT` trigger can trim surrounding spaces and normalize case:

```sql
DELIMITER //

CREATE TRIGGER trg_TriggerPracticeContact_NormalizeEmail
BEFORE INSERT ON TriggerPracticeContact
FOR EACH ROW
BEGIN
    SET NEW.EmailAddress = LOWER(TRIM(NEW.EmailAddress));
END //

DELIMITER ;
```

After creating the trigger:

```sql
INSERT INTO TriggerPracticeContact (EmailAddress)
VALUES ('  Student@Example.com  ');

SELECT ContactId, EmailAddress
FROM TriggerPracticeContact
ORDER BY ContactId DESC
LIMIT 1;
```

The stored email address is `student@example.com`.

## Example: Validate an Insert

A trigger can reject invalid data with `SIGNAL`:

```sql
CREATE TABLE TriggerPracticeProduct (
    ProductId INT AUTO_INCREMENT PRIMARY KEY,
    ProductName VARCHAR(100) NOT NULL,
    Price DECIMAL(10, 2) NOT NULL
);
```

```sql
DELIMITER //

CREATE TRIGGER trg_TriggerPracticeProduct_ValidatePrice
BEFORE INSERT ON TriggerPracticeProduct
FOR EACH ROW
BEGIN
    IF NEW.Price < 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Price cannot be negative';
    END IF;
END //

DELIMITER ;
```

The insert fails with a database error if the price is negative. The row is not inserted.

Use table constraints such as `NOT NULL`, `CHECK`, `UNIQUE`, and foreign keys when they can express the rule directly. A trigger is useful for rules that need procedural logic or cross-table behavior, but it should not replace a suitable constraint.

## Example: Audit an Update

An `AFTER UPDATE` trigger can record a price change:

```sql
CREATE TABLE TriggerPracticePriceAudit (
    AuditId INT AUTO_INCREMENT PRIMARY KEY,
    ProductId INT NOT NULL,
    OldPrice DECIMAL(10, 2) NOT NULL,
    NewPrice DECIMAL(10, 2) NOT NULL,
    ChangedAt TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

```sql
DELIMITER //

CREATE TRIGGER trg_TriggerPracticeProduct_AuditPrice
AFTER UPDATE ON TriggerPracticeProduct
FOR EACH ROW
BEGIN
    IF OLD.Price <> NEW.Price THEN
        INSERT INTO TriggerPracticePriceAudit
            (ProductId, OldPrice, NewPrice)
        VALUES
            (OLD.ProductId, OLD.Price, NEW.Price);
    END IF;
END //

DELIMITER ;
```

After an update, inspect the audit row:

```sql
UPDATE TriggerPracticeProduct
SET Price = Price + 1.00
WHERE ProductId = 1;

SELECT ProductId, OldPrice, NewPrice, ChangedAt
FROM TriggerPracticePriceAudit
WHERE ProductId = 1
ORDER BY AuditId DESC;
```

The trigger logs only changes where the old and new prices differ.

## Trigger Errors and Transactions

A trigger runs as part of the statement that caused it. With a transactional storage engine such as InnoDB, an error in the trigger can cause the triggering statement to fail; its changes participate in the surrounding transaction.

Triggers cannot start or end transactions with statements such as `START TRANSACTION`, `COMMIT`, or `ROLLBACK`. The application or calling procedure controls the transaction.

An `AFTER` trigger does not mean “after the transaction commits.” It means after the row operation, while the statement and transaction are still in progress.

---

## Limitations and Design Considerations

- Triggers execute once per affected row; a bulk statement may invoke the trigger many times.
- A trigger cannot return a result set to the client. Use an audit or related table when a durable record is needed.
- A trigger cannot modify a table that is already being used by the statement that invoked the trigger. Design cross-table logic with this limitation in mind.
- Use `BEFORE` triggers to validate or adjust permitted `NEW` values.
- Use `AFTER` triggers when the row operation must succeed before recording its result in another table.
- Avoid slow queries and unnecessary work in trigger bodies.
- Document trigger side effects so application developers know what a DML statement does.
- A trigger is not a substitute for authorization checks in an application.
- `TRUNCATE TABLE` is not a row-by-row `DELETE` and does not activate `DELETE` triggers.

## Managing Triggers

List triggers in the current database:

```sql
SHOW TRIGGERS;
```

Inspect a trigger definition:

```sql
SHOW CREATE TRIGGER trg_TriggerPracticeProduct_AuditPrice;
```

Remove a trigger by its exact name:

```sql
DROP TRIGGER IF EXISTS trg_TriggerPracticeProduct_AuditPrice;
```

Dropping a trigger does not delete rows already written to an audit table.

---

## Testing and Troubleshooting

When testing a trigger:

1. Confirm the trigger is attached to the expected table, timing, and event.
2. Run one statement that should activate it.
3. Inspect the changed row or audit table.
4. Test a boundary or invalid value if the trigger validates data.
5. Check whether the DML statement ran inside a transaction.
6. Inspect errors and the trigger definition with `SHOW CREATE TRIGGER`.

Because trigger execution is automatic, test the side effects as carefully as the direct statement result.

## Summary

| Trigger Feature | Use |
| --------------- | --- |
| `BEFORE INSERT` | Validate or adjust a new row |
| `AFTER INSERT` | Record or react to an inserted row |
| `BEFORE UPDATE` | Validate or adjust proposed changes |
| `AFTER UPDATE` | Record or react to completed row changes |
| `BEFORE DELETE` | Validate or record information before removal |
| `AFTER DELETE` | Record or react to a removed row |
| `NEW` | Access inserted or proposed column values |
| `OLD` | Access prior or deleted column values |
| `SIGNAL` | Reject a row with a clear database error |

Triggers automate row-level behavior. Keep their side effects small, visible, and well tested.
