# MySQL Transactions

## What Is a Transaction?

A **transaction** is a group of database operations treated as one unit of work. The transaction either commits its changes or rolls them back.

Transactions are important when several changes must succeed or fail together. For example, transferring money requires both a debit and a credit. If only one update succeeds, the data becomes inconsistent.

This guide expands on the introductory [MySQL Transactions](./Transactions.md) example. The SQL examples use MySQL 8.0 and InnoDB tables.

---

## The ACID Properties

Transactions are commonly described by the **ACID** properties:

| Property | Meaning |
| -------- | ------- |
| **Atomicity** | All operations in a transaction succeed together, or the transaction's changes are rolled back. |
| **Consistency** | A transaction moves the database from one valid state to another, obeying constraints and application rules. |
| **Isolation** | Concurrent transactions are controlled so their operations do not produce invalid observations or conflicting writes. |
| **Durability** | After a transaction commits, its changes are persisted according to the database's durability configuration. |

ACID is a set of goals, not a guarantee that every query is correct. The application must still validate its inputs, update the correct rows, and handle errors.

## Transactional Tables

Transactions work only for storage engines that support them. In MySQL, **InnoDB** is the usual transactional storage engine.

Check a table's engine with:

```sql
SHOW TABLE STATUS LIKE 'TransactionPracticeAccount';
```

For a practice table, select InnoDB explicitly:

```sql
CREATE TABLE TransactionPracticeAccount (
    AccountId INT PRIMARY KEY,
    Holder VARCHAR(100) NOT NULL,
    Balance DECIMAL(12, 2) NOT NULL
) ENGINE = InnoDB;
```

If a statement changes a nontransactional table, `ROLLBACK` cannot undo those changes.

## Starting, Committing, and Rolling Back

Use `START TRANSACTION` to begin an explicit transaction:

```sql
START TRANSACTION;

UPDATE TransactionPracticeAccount
SET Balance = Balance - 100.00
WHERE AccountId = 1;

UPDATE TransactionPracticeAccount
SET Balance = Balance + 100.00
WHERE AccountId = 2;

COMMIT;
```

`COMMIT` makes the transaction's changes permanent. Until then, they are uncommitted.

If the operation should not be kept, use `ROLLBACK`:

```sql
START TRANSACTION;

UPDATE TransactionPracticeAccount
SET Balance = Balance + 500.00
WHERE AccountId = 2;

ROLLBACK;
```

The update is undone, provided the table uses a transactional engine and no implicit commit occurred.

## Autocommit

MySQL sessions normally use **autocommit**. When autocommit is enabled, each statement outside an explicit transaction is committed as its own transaction.

Check the current setting:

```sql
SELECT @@autocommit;
```

With autocommit enabled:

```sql
UPDATE TransactionPracticeAccount
SET Balance = Balance + 10.00
WHERE AccountId = 1;
```

That statement commits when it completes. To group multiple statements together, explicitly start a transaction.

Avoid changing `autocommit` as a shortcut for controlling one operation. Use explicit transaction boundaries so it is clear which statements belong together.

## Savepoints

A **savepoint** marks a position inside a transaction. You can roll back to it without undoing all earlier work.

```sql
START TRANSACTION;

UPDATE TransactionPracticeAccount
SET Balance = Balance - 200.00
WHERE AccountId = 1;

SAVEPOINT after_debit;

UPDATE TransactionPracticeAccount
SET Balance = Balance + 200.00
WHERE AccountId = 2;

-- Undo the credit, but keep the earlier debit.
ROLLBACK TO SAVEPOINT after_debit;

UPDATE TransactionPracticeAccount
SET Balance = Balance + 200.00
WHERE AccountId = 3;

COMMIT;
```

`ROLLBACK TO SAVEPOINT` does not end the transaction. The transaction remains active and must eventually be committed or rolled back. A savepoint can be removed with `RELEASE SAVEPOINT name`; committing or fully rolling back also removes the transaction's savepoints.

Savepoints are not nested transactions. They provide rollback points within one transaction.

## Isolation Levels and Concurrent Work

Isolation levels control how a transaction can observe work performed by concurrent transactions. MySQL InnoDB supports:

- `READ UNCOMMITTED`
- `READ COMMITTED`
- `REPEATABLE READ`
- `SERIALIZABLE`

InnoDB's default isolation level is commonly `REPEATABLE READ`, but a session or server can be configured differently.

| Phenomenon | Description |
| ---------- | ----------- |
| Dirty read | A transaction reads changes another transaction has not committed. |
| Non-repeatable read | A row read again in the same transaction has a different committed value. |
| Phantom read | Repeating a range query returns a different set of rows. |

InnoDB uses multiversion concurrency control (MVCC) for many ordinary reads. A plain `SELECT` can read a consistent snapshot without blocking a concurrent writer. Writes and locking reads may still wait for locks.

Set the isolation level for the next transaction before starting it:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
```

Changing the isolation level affects what a transaction can observe; it is not a replacement for correct locking or application logic.

## Locking Reads

When a transaction must read rows and then modify them without another transaction changing them first, use a locking read where appropriate:

```sql
START TRANSACTION;

SELECT AccountId, Balance
FROM TransactionPracticeAccount
WHERE AccountId = 1
FOR UPDATE;

UPDATE TransactionPracticeAccount
SET Balance = Balance - 50.00
WHERE AccountId = 1;

COMMIT;
```

`FOR UPDATE` requests locks on the selected rows for the transaction. Other transactions that need conflicting locks may wait until this transaction commits or rolls back.

Use a selective predicate supported by an appropriate index. A locking query that examines many rows can block more work than intended.

## Errors, Deadlocks, and Retries

A transaction should be rolled back if an operation fails and the overall unit of work cannot safely continue.

InnoDB can detect a deadlock and choose one transaction as the victim, rolling it back so the other can proceed. Applications should be prepared to retry the **entire transaction** when a deadlock is reported, not just the final statement.

Keep transactions short and access shared rows in a consistent order. Do not pause for user input, make slow network calls, or perform unrelated work while holding locks.

Deadlocks are distinct from lock waits: a lock wait can resolve when another transaction finishes, while a deadlock is a cycle of transactions waiting on each other.

---

## Implicit Commits and DDL

Some MySQL statements cause an implicit commit. Many DDL statements, such as `CREATE TABLE`, `ALTER TABLE`, and `DROP TABLE`, can commit an active transaction. Do not assume that DDL can be rolled back with ordinary DML.

Complete schema changes outside a transaction that is intended to protect application data. Check the MySQL documentation for the exact implicit-commit behavior of a statement before combining it with transactional work.

---

## A Safe Transaction Workflow

For a multi-step data change:

1. Confirm the affected tables use a transactional engine.
2. Begin a transaction immediately before the related work.
3. Use precise predicates and check that the expected rows were affected.
4. Apply all required changes.
5. Verify the resulting data while still in the transaction when appropriate.
6. Commit only when the complete operation is valid.
7. Roll back on errors or failed validation.
8. Keep the transaction short and handle deadlock retries at the application boundary.

Use a transaction for atomicity, but also use constraints and validation to prevent invalid states.

## Common Mistakes

### Forgetting to Commit or Roll Back

An open transaction can retain locks and cause other work to wait. End every explicit transaction.

### Assuming `ROLLBACK` Undoes Everything

Rollback applies to changes made in the current transaction on transactional tables. It cannot undo already committed work, nontransactional-table changes, or statements that caused an implicit commit.

### Performing Unrelated Work Inside a Transaction

Long-running transactions hold resources and can increase blocking. Keep the transaction focused on the unit of work.

### Ignoring Affected-Row Counts

A transaction can commit successfully even if an `UPDATE` matched zero rows. Check that the expected rows were affected before committing.

### Retrying Only One Statement After a Deadlock

A deadlock victim's transaction is rolled back. Retry the complete logical operation from a clean transaction boundary.

### Treating Savepoints as Nested Transactions

A savepoint does not commit earlier work independently. The whole transaction still commits or rolls back as one unit.

## Summary

| Command or Concept | Purpose |
| ------------------ | ------- |
| `START TRANSACTION` | Begin an explicit transaction |
| `COMMIT` | Persist the transaction's changes |
| `ROLLBACK` | Undo uncommitted transactional changes |
| `SAVEPOINT` | Mark a rollback point inside a transaction |
| `ROLLBACK TO SAVEPOINT` | Undo work since a savepoint without ending the transaction |
| Autocommit | Commit each standalone statement automatically |
| Isolation level | Control visibility of concurrent changes |
| `SELECT ... FOR UPDATE` | Read rows while requesting update locks |
| InnoDB | MySQL storage engine commonly used for transactional tables |

Transactions make related data changes atomic, but they must be paired with correct validation, short transaction scopes, and reliable error handling.
