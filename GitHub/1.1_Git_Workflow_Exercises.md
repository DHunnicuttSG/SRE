# Git Workflow Exercises

These exercises use a class repository or a personal practice repository created for training. Do not use the instructor's source repository unless explicitly asked. Never commit credentials, private keys, personal access tokens, or real customer data.

## Prerequisites

- Git is installed and available in a terminal.
- You have access to an approved GitHub practice repository, or your instructor has provided a local repository as an alternative.
- You have configured an author name and an approved email address.
- You know the repository URL and the default branch name used in class.

The angle-bracketed values below are placeholders; replace them with instructor-provided values.

---

## Exercise 1: Clone and Inspect

1. Clone the approved practice repository:

   ```bash
   git clone <repository-url>
   ```

2. Enter the cloned directory.
3. Use `git status`, `git remote -v`, and `git log --oneline -5`.
4. Record:
   - The current branch
   - The remote name and URL
   - The most recent commit message
   - Whether the working tree is clean

**Checkpoint:** Explain why cloning creates a local repository and which remote name Git creates by default.

---

## Exercise 2: Make and Commit a Change

1. Create a topic branch named `docs/<your-name>-first-change`.
2. Add a short section to the training README using only non-sensitive information.
3. Review the change with `git status` and `git diff`.
4. Stage only the intended file.
5. Review the staged change with `git diff --staged`.
6. Commit with a message describing the change.
7. Use `git log --oneline -3` and `git status` to verify the result.

**Checkpoint:** Is the new commit visible on GitHub yet? Explain your answer.

---

## Exercise 3: Push a Topic Branch

1. Push your branch and set its upstream:

   ```bash
   git push -u origin docs/<your-name>-first-change
   ```

2. Verify the branch appears in the approved remote repository.
3. Open a pull request if the class repository supports it.
4. Include a short description and review the pull-request diff.

If you are working locally without a remote, explain what `git push` would do when a remote is available.

**Checkpoint:** State what the `-u` option records.

---

## Exercise 4: Fetch, Inspect, and Pull

Work with an instructor or partner who can make a new commit on the shared practice repository's default branch.

1. Ensure your local default branch has no uncommitted changes.
2. Switch to the default branch.
3. Before fetching, record the output of `git status -sb`.
4. Fetch updates:

   ```bash
   git fetch origin
   ```

5. Check `git status -sb` again and inspect new remote commits:

   ```bash
   git log --oneline HEAD..origin/main
   ```

   Substitute the actual default branch for `main` if necessary.
6. Confirm that fetching alone did not change your checked-out files.
7. Integrate the update using fast-forward-only pull:

   ```bash
   git pull --ff-only origin main
   ```

8. Verify the new file or change and confirm the branch status.

**Checkpoint:** Explain what changed after `fetch` and what changed after `pull`.

---

## Exercise 5: Review and Safe Cleanup

1. Inspect your commit and pull-request history.
2. Review `.gitignore` and identify one appropriate local-only file pattern.
3. Confirm no secrets or unrelated files are staged or pushed.
4. If you have an unstaged edit that you want to keep but accidentally staged, unstage it with:

   ```bash
   git restore --staged <file>
   ```

5. Explain why `git restore <file>` is different and potentially destructive.

**Checkpoint:** Submit a short workflow note covering clone, branch, stage, commit, fetch, pull, and push.

---

## Optional Challenge: Resolve a Conflict

With instructor approval, have two learners edit the same paragraph on separate branches. Integrate one change, then attempt to integrate the other.

1. Use `git status` to identify the conflicted file.
2. Resolve the file while preserving the intended content.
3. Remove conflict markers, review the diff, and test the result.
4. Complete the merge using the class workflow.

Do not force-push or rewrite shared history to bypass the conflict.
