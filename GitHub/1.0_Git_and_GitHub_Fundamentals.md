# Git and GitHub Fundamentals

## Learning Objectives

After working through this lesson, you should be able to:

- Explain the difference between Git and GitHub.
- Clone a remote repository and inspect its state.
- Stage and commit a focused change.
- Explain the difference between `git fetch`, `git pull`, and `git push`.
- Use branches and pull requests for collaborative changes.
- Protect credentials and other sensitive data from being committed.

## Git and GitHub

**Git** is a distributed version control system. It records snapshots of files as commits and lets people work on separate branches.

**GitHub** is a hosting and collaboration service for Git repositories. It adds remote hosting, pull requests, code review, issues, and related project tools.

Git can be used without GitHub. GitHub repositories use Git to track changes.

---

## The Main Areas in a Git Workflow

A common local workflow moves changes through these areas:

1. **Working tree:** The files you currently see and edit.
2. **Staging area (index):** The exact changes selected for the next commit.
3. **Local repository:** Commits stored on your computer.
4. **Remote repository:** A repository hosted elsewhere, often on GitHub.

```text
Working tree --git add--> Staging area --git commit--> Local repository
                                                           |
                                                     git push / git fetch
                                                           |
                                                     Remote repository
```

`git pull` fetches remote changes and integrates them into the current branch.

### A Commit Is Not a Push

- `git commit` records staged changes in your **local** repository.
- `git push` sends local commits to a remote repository.

A commit can exist on your computer without appearing on GitHub.

## Configure Your Identity

Git records an author name and email with commits. Configure an identity appropriate for your class or organization:

```bash
git config --global user.name "Your Name"
git config --global user.email "your-approved-email@example.com"
```

Review the configured values:

```bash
git config --global --list
```

Do not include passwords, personal access tokens, or private keys in Git configuration or repository files. Your instructor may ask you to set identity for only the current repository by omitting `--global`.

## Clone a Repository

`git clone` creates a local copy of a remote repository, including its commit history, and configures the remote named `origin` by default.

```bash
git clone <repository-url>
cd <repository-folder>
```

Inspect the repository:

```bash
git status
git remote -v
git log --oneline --decorate -5
```

The URL is supplied by the instructor or copied from the approved GitHub repository page. Do not put credentials in the URL.

## Check Changes Before Committing

Use `git status` frequently:

```bash
git status
git status --short
```

`git diff` shows unstaged changes in tracked files:

```bash
git diff
```

`git add` selects changes for the next commit:

```bash
git add README.md
```

You can stage multiple named files. Review what is staged before committing:

```bash
git diff --staged
```

Use `git add -A` only when you have reviewed all changed and untracked files. It may stage files you did not intend to include.

---

## Commit a Change

A commit records the staged snapshot in the local repository:

```bash
git commit -m "Document local setup steps"
```

Write a short message that describes the change. Before committing, confirm:

1. The diff contains only intended changes.
2. No credentials, generated files, or unrelated work are staged.
3. The staged diff matches the commit message.

Inspect commits and a specific commit:

```bash
git log --oneline --graph --decorate -10
git show --stat
git show <commit-id>
```

## Branches and Pull Requests

A branch is an independent line of development. Create a topic branch before making a change:

```bash
git switch -c docs/update-setup-guide
```

Check the current branch:

```bash
git branch --show-current
git branch
```

Branches keep work separate until it is reviewed and integrated. On GitHub, a **pull request** proposes merging a branch into another branch. Reviewers can discuss the change and request updates.

Before switching branches, check `git status`. Git may prevent a switch if uncommitted changes would be overwritten.

---

## Fetch: See What Is on the Remote

`git fetch` downloads remote objects and updates remote-tracking references such as `origin/main`. It does **not** merge those changes into your current branch or replace your working files.

```bash
git fetch origin
```

Inspect the remote and compare your current branch with the fetched `main` branch:

```bash
git status -sb
git log --oneline HEAD..origin/main
git diff HEAD..origin/main
```

Fetch is useful when you want to inspect remote changes before deciding how to integrate them.

---

## Pull: Fetch and Integrate

`git pull` fetches from a remote and integrates the selected remote branch into your current branch. Depending on configuration and command options, integration may use a fast-forward, merge, or rebase.

For a beginner workflow that refuses to create a merge commit automatically when branches have diverged:

```bash
git switch main
git pull --ff-only origin main
```

If `--ff-only` reports that the branches have diverged, stop and inspect the situation. Do not force the update. Ask the instructor or follow the team's documented merge/rebase process.

Before pulling into a branch, check for uncommitted work:

```bash
git status
```

Commit or otherwise safely preserve intended changes before integrating remote work.

### Fetch Versus Pull

| Command | Downloads remote changes? | Changes current branch or working files? |
| ------- | ------------------------- | ----------------------------------------- |
| `git fetch` | Yes | No |
| `git pull` | Yes | Yes, by integrating the selected remote branch |

Use `fetch` to inspect first; use `pull` when you intend to integrate.

---

## Push: Publish Local Commits

`git push` sends local commits to a remote branch:

```bash
git push -u origin docs/update-setup-guide
```

The `-u` option sets the upstream branch for future pushes and pulls. After it is set, the following is usually sufficient:

```bash
git push
```

Push a topic branch and open a pull request rather than pushing directly to a protected shared branch. If a push is rejected because the remote has new commits, fetch and inspect the changes, then use the team's integration process. Do not use `git push --force` to bypass a rejection on shared work.

## A Safe Feature-Branch Workflow

This example shows a typical small change:

```bash
git clone <repository-url>
cd <repository-folder>
git status

git switch -c docs/update-setup-guide

# Edit the intended file, then review the change.
git status
git diff
git add README.md
git diff --staged
git commit -m "Document local setup steps"

git fetch origin
git status -sb
git push -u origin docs/update-setup-guide
```

Then open a pull request on GitHub, describe the change, review the diff, respond to feedback, and wait for approval before merging.

To update your local `main` branch separately:

```bash
git switch main
git pull --ff-only origin main
```

Follow your instructor's or team's branch policy when updating a feature branch with newer `main` changes.

## Other Useful Commands

| Command | Purpose |
| ------- | ------- |
| `git status` | Show the current branch and working/staged state |
| `git diff` | Show unstaged tracked changes |
| `git diff --staged` | Show staged changes |
| `git log --oneline --graph --all` | Visualize commit history and branches |
| `git remote -v` | Show configured remotes |
| `git branch --show-current` | Show the current branch |
| `git switch <branch>` | Switch to an existing branch |
| `git switch -c <branch>` | Create and switch to a branch |
| `git restore <file>` | Discard unstaged changes in a file; use carefully |
| `git restore --staged <file>` | Unstage a file while keeping its working-tree changes |
| `git show <commit>` | Inspect a commit |
| `git rm <file>` | Remove a tracked file and stage the removal |

Avoid destructive cleanup commands such as `git reset --hard` unless you understand exactly what will be lost and have authorization to use them.

## Conflicts and Recovery

A **merge conflict** occurs when Git cannot automatically combine changes to the same part of a file.

1. Read `git status` to identify conflicted files.
2. Open each file and review the conflict markers.
3. Keep the intended content and remove the markers.
4. Test the result.
5. Stage the resolved file and complete the merge or rebase using the workflow in use.

Do not choose a side without understanding the change. If uncertain, preserve the work and ask for review.

For an accidental staging operation:

```bash
git restore --staged <file>
```

This unstages the file but keeps the working-tree changes. `git restore <file>` can discard unstaged edits, so inspect `git diff` first.

## Protecting Secrets and Repository Hygiene

- Use `.gitignore` for local-only files, generated output, and environment-specific artifacts.
- Review `git status` and `git diff --staged` before every commit.
- Never commit passwords, tokens, private keys, `.env` files containing secrets, or real customer data.
- A secret remains exposed in repository history even if you later delete the file. If a secret is committed, notify the owner and rotate/revoke it immediately.
- Use the approved credential manager or SSH setup. Never paste access tokens into a Git remote URL or a public issue.
- Push only to repositories and branches where you have permission.

## Common Misunderstandings

### “Commit sends my change to GitHub.”

No. Commit saves it locally. Push publishes commits to a remote.

### “Fetch updates my files.”

Fetch updates remote-tracking references and downloads data. It does not change the checked-out branch or working files.

### “Pull is always a simple download.”

Pull also integrates the selected remote branch. It can change the current branch and may encounter divergence or conflicts.

### “Push uploads every modified file.”

Push sends commits, not arbitrary working-tree changes. Changes must be staged and committed first.

### “Deleting a secret file removes the secret.”

Deleting it in a later commit does not erase it from prior commits. Rotate the secret and follow the repository's incident process.
