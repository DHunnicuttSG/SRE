# SQL Common Table Expressions (CTEs)

## What Is a CTE?

A **common table expression**, or **CTE**, is a named query that is available to one SQL statement. A CTE is introduced with `WITH` and can be referenced by the statement that follows it.

CTEs can make complex SQL easier to understand by giving intermediate results meaningful names. They are useful for:

- Breaking a query into logical steps
- Reusing an intermediate result in one statement
- Separating aggregation from joins or filtering
- Organizing window-function queries
- Traversing hierarchical data with a recursive CTE

The examples in this guide use MySQL 8.0 and the `PersonalTrainer` database.

---

## A Basic CTE

The simplest CTE defines a name and a query, then uses that name in the following statement:

```sql
WITH WorkoutDurations AS (
    SELECT
        WorkoutId,
        `Name`,
        LevelId,
        MinMinutes,
        MaxMinutes
    FROM Workout
)
SELECT
    WorkoutDurations.`Name` WorkoutName,
    WorkoutDurations.MinMinutes,
    WorkoutDurations.MaxMinutes
FROM WorkoutDurations
WHERE WorkoutDurations.MaxMinutes >= 60
ORDER BY WorkoutDurations.MaxMinutes DESC, WorkoutDurations.`Name`;
```

The CTE name behaves like a table name within the statement. Its scope ends when the statement finishes; it is not a permanent table or a session-wide temporary table.

---

## CTE Syntax

The general structure is:

```sql
WITH cte_name AS (
    SELECT ...
)
SELECT ...
FROM cte_name;
```

A statement may define more than one CTE. Separate the definitions with commas:

```sql
WITH first_cte AS (
    SELECT ...
),
second_cte AS (
    SELECT ...
)
SELECT ...
FROM first_cte
JOIN second_cte ON ...;
```

The CTE definitions appear directly before the statement that uses them. In MySQL, one `WITH` clause may be used for a statement; later CTEs in the same list can refer to earlier CTEs.

## Aggregate in a CTE Before Joining

This CTE counts each Client's Goals before joining the counts to Client:

```sql
WITH GoalCounts AS (
    SELECT
        cg.ClientId,
        COUNT(*) GoalCount
    FROM ClientGoal cg
    GROUP BY cg.ClientId
)
SELECT
    c.ClientId,
    c.FirstName,
    c.LastName,
    COALESCE(gc.GoalCount, 0) GoalCount
FROM Client c
LEFT JOIN GoalCounts gc ON c.ClientId = gc.ClientId
ORDER BY c.LastName, c.FirstName;
```

`GoalCounts` has one row per Client who has a Goal. The `LEFT JOIN` keeps Clients who have none, and `COALESCE()` displays their missing count as zero.

The CTE makes the aggregation step explicit and keeps the outer query focused on combining results.

## Multiple CTEs

Separate CTEs can calculate different results at the same level of detail. This avoids accidentally multiplying rows when joining two one-to-many relationships.

```sql
WITH ClientCounts AS (
    SELECT
        cg.GoalId,
        COUNT(*) ClientCount
    FROM ClientGoal cg
    GROUP BY cg.GoalId
),
WorkoutCounts AS (
    SELECT
        wg.GoalId,
        COUNT(*) WorkoutCount
    FROM WorkoutGoal wg
    GROUP BY wg.GoalId
)
SELECT
    g.GoalId,
    g.`Name` GoalName,
    COALESCE(cc.ClientCount, 0) ClientCount,
    COALESCE(wc.WorkoutCount, 0) WorkoutCount
FROM Goal g
LEFT JOIN ClientCounts cc ON g.GoalId = cc.GoalId
LEFT JOIN WorkoutCounts wc ON g.GoalId = wc.GoalId
ORDER BY g.`Name`;
```

If ClientGoal and WorkoutGoal were joined directly before counting, the matching rows could multiply. For example, a Goal with five Clients and three Workouts could produce fifteen joined rows. Aggregating each relationship separately preserves the correct counts.

## CTEs for Multi-Step Aggregation

The following example calculates paid invoice totals for each Client and then selects totals greater than $1,000:

```sql
WITH PaidTotals AS (
    SELECT
        i.ClientId,
        SUM(li.Price * li.Quantity) PaidTotal
    FROM Invoice i
    INNER JOIN InvoiceLineItem li ON i.InvoiceId = li.InvoiceId
    WHERE i.InvoiceStatus = 2
    GROUP BY i.ClientId
)
SELECT
    c.ClientId,
    c.FirstName,
    c.LastName,
    pt.PaidTotal
FROM Client c
INNER JOIN PaidTotals pt ON c.ClientId = pt.ClientId
WHERE pt.PaidTotal > 1000.00
ORDER BY c.LastName, c.FirstName;
```

`PaidTotals` expresses one step: calculate a paid total per Client. The outer query handles Client details and the threshold. In the exercise dataset, 146 Clients match.

## CTEs with Window Functions

A CTE can hold window-function results so that an outer query can filter them:

```sql
WITH WorkoutLevelAverages AS (
    SELECT
        w.WorkoutId,
        w.`Name`,
        w.LevelId,
        w.MaxMinutes,
        AVG(w.MaxMinutes) OVER (
            PARTITION BY w.LevelId
        ) AverageMaxMinutes
    FROM Workout w
)
SELECT
    WorkoutLevelAverages.`Name` WorkoutName,
    WorkoutLevelAverages.LevelId,
    WorkoutLevelAverages.MaxMinutes,
    WorkoutLevelAverages.AverageMaxMinutes
FROM WorkoutLevelAverages
WHERE WorkoutLevelAverages.MaxMinutes > WorkoutLevelAverages.AverageMaxMinutes
ORDER BY WorkoutLevelAverages.LevelId, WorkoutLevelAverages.MaxMinutes DESC;
```

The CTE calculates the average on each row. The outer query filters using that calculated value. For more about window syntax and behavior, see [SQL Window Functions](./2.1_Window_Functions.md).

## Recursive CTEs

A **recursive CTE** refers to itself. It has two parts:

1. **Anchor query:** Produces the starting rows.
2. **Recursive query:** Uses rows already found to produce more rows.

The parts are joined with `UNION ALL`. MySQL repeats the recursive query until it produces no new rows or reaches its recursion limit.

### Traverse Exercise Categories

`ExerciseCategory` has a self-referencing `ParentCategoryId`. The following recursive CTE starts at root categories and follows each category's children:

```sql
WITH RECURSIVE CategoryTree AS (
    SELECT
        ec.ExerciseCategoryId,
        ec.ParentCategoryId,
        ec.`Name`,
        0 Depth,
        CAST(ec.`Name` AS CHAR(1000)) CategoryPath
    FROM ExerciseCategory ec
    WHERE ec.ParentCategoryId IS NULL

    UNION ALL

    SELECT
        child.ExerciseCategoryId,
        child.ParentCategoryId,
        child.`Name`,
        parent.Depth + 1,
        CONCAT(parent.CategoryPath, ' > ', child.`Name`)
    FROM ExerciseCategory child
    INNER JOIN CategoryTree parent
        ON child.ParentCategoryId = parent.ExerciseCategoryId
)
SELECT
    CategoryTree.ExerciseCategoryId,
    CategoryTree.ParentCategoryId,
    CategoryTree.`Name` CategoryName,
    CategoryTree.Depth,
    CategoryTree.CategoryPath
FROM CategoryTree
ORDER BY CategoryTree.CategoryPath;
```

The anchor query finds categories whose parent is `NULL`. Each recursive step adds categories whose parent is already in `CategoryTree`.

The `CAST()` sets an adequate type for `CategoryPath` in the anchor query. Recursive CTE column types are based on the anchor, so a short inferred string type can be insufficient when recursive steps append text.

### Recursive CTE Safety

Recursive queries need a clear stopping condition. In a well-formed parent-child hierarchy, recursion stops when no child points to a category in the current result. If the data can contain cycles, add cycle detection so the query cannot revisit the same node indefinitely. MySQL also enforces a recursion-depth limit; very deep hierarchies may require reviewing that limit.

## CTEs Versus Derived Tables

A derived table is a subquery in the `FROM` clause. A CTE is a named query defined before the main statement.

| Derived Table | CTE |
| ------------- | --- |
| Defined inline where it is used | Defined at the start of the statement |
| Can be concise for one small intermediate result | Can give multi-step queries clearer names |
| Usually referenced at its inline location | Can be referenced by the main query, and in some cases by multiple parts of it |
| Does not directly express recursive traversal | Can be recursive with `WITH RECURSIVE` |

Neither form is automatically faster in every case. The optimizer decides how to execute a query; use `EXPLAIN` and measurements when performance matters.

## Common Mistakes

### Expecting a CTE to Persist

A CTE exists only for the statement immediately following its `WITH` clause. Use a permanent table or a temporary table if the result must be available to later statements.

### Forgetting the Outer Query

A CTE definition is not a complete statement on its own. It must be followed by a statement that uses it.

### Joining Before Aggregating

Joining multiple one-to-many relationships before aggregating can multiply rows and inflate counts or sums. Aggregate each relationship to the intended grain first, then join the results.

### Assuming CTEs Always Improve Performance

CTEs improve organization, but they are not a guarantee of faster execution. Inspect the execution plan for performance-sensitive queries.

### Leaving a Recursive Query Without a Base Case

The anchor query determines where recursion starts. If it returns no rows, the recursive CTE returns no rows. If recursive data can cycle, add cycle prevention.

## A Practical Workflow

When building a query with CTEs:

1. Break the problem into intermediate results.
2. Decide the grain of each result, such as one row per Client or one row per Invoice.
3. Give each CTE a descriptive name.
4. Test each CTE's inner query independently.
5. Join intermediate results using their keys.
6. Check whether `LEFT JOIN` is needed to preserve rows with no match.
7. For recursive CTEs, identify the anchor, the recursive relationship, and the stopping condition.
8. Use `EXPLAIN` if performance needs investigation.

## Summary

| CTE Pattern | Use |
| ----------- | --- |
| Single CTE | Name one intermediate result |
| Multiple CTEs | Separate logically independent calculations |
| Aggregate CTE | Summarize rows before joining or filtering |
| CTE with window function | Calculate a window value and filter it in the outer query |
| Recursive CTE | Traverse hierarchical or repeated relationships |

Use CTEs to make query steps and their row granularity clear. They improve readability, but correct joins, aggregation, and execution-plan analysis still matter.
