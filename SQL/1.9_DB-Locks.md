# Database Locks

## What Is a Database Lock?

A **database lock** is a control mechanism that prevents concurrent transactions from making conflicting changes or reading inconsistent data.

Locks help databases enforce the **ACID** properties, especially:

- **Isolation:** Transactions operate as if they are separated from one another.
- **Consistency:** Transactions follow constraints and rules.
- **Atomicity:** Incomplete work is rolled back rather than left partially applied.

Databases use locks to manage thousands of simultaneous sessions safely.
The goal is to allow as much concurrency as possible without allowing conflicting operations to corrupt or misrepresent data.

---

## A Simple Example

Alice and Bob both try to update the last available ticket for an event.

```sql
START TRANSACTION;

UPDATE tickets
SET status = 'sold'
WHERE ticket_id = 501
  AND status = 'available';
```

The database must ensure that only one transaction successfully sells ticket `501`.

The first transaction that updates the row holds a lock on the row.
The second transaction may wait until the first transaction commits or rolls back.
Afterward, it will evaluate the row again under the database's locking and transaction rules.

---

## Lock Versus Transaction

A lock belongs to the **transaction** that acquired it.

If a transaction:

- Commits, its locks are released.
- Rolls back, its changes and locks are released.
- Remains open, the locks may remain in place.

This is why applications should:

- Keep transactions short.
- Commit or roll back as soon as possible.
- Avoid waiting for human input inside an open transaction.
- Catch errors and roll back failed work.

```sql
START TRANSACTION;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 10;

COMMIT;
```

## Shared and Exclusive Locks

### Shared Lock

A **shared lock** is used when a transaction needs to read data while preventing conflicting writes.
Many transactions may hold shared locks on the same resource.

It is sometimes called a **read lock**.

### Exclusive Lock

An **exclusive lock** is used when a transaction needs to modify data.
Other transactions are generally prevented from modifying or locking the same resource.

It is sometimes called a **write lock**.

| Lock Type | Can Read? | Can Update? | Typical Use |
| --------- | --------- | ----------- | ----------- |
| Shared | Yes | No | Reading data with lock protection |
| Exclusive | Usually no for the other transaction | No | Inserting, updating, or deleting |

Exact behavior depends on the database engine and isolation level.
For example, many modern databases allow one transaction to read a consistent snapshot while another holds an exclusive row lock.

---

## Lock Granularity

Lock **granularity** describes how much of a database is protected.

### Row-Level Locks

A row-level lock protects one row or a small set of rows.

Benefits:

- High concurrency
- One transaction can update one row while another updates a different row

Costs:

- Many locks may be needed for large updates
- Lock coordination is more complex

MySQL's InnoDB storage engine commonly uses row-level locks.

### Table-Level Locks

A table-level lock protects an entire table.

Benefits:

- Simple to coordinate
- Efficient for operations affecting most or all of a table

Costs:

- Blocks or limits work in unrelated rows

### Page-Level Locks

Some database systems use page-level locks.
A page is a fixed-size storage unit that may contain several rows.

---

## Lock Escalation

**Lock escalation** occurs when a database converts many fine-grained locks into one larger lock.

For example, locking thousands of individual rows might consume more memory or coordination than locking the containing table.

If an engine escalates row locks to a table lock, transactions updating one row may unexpectedly block transactions updating unrelated rows.
Database behavior differs by engine and configuration.

---

## Pessimistic and Optimistic Locking

### Pessimistic Locking

Pessimistic locking assumes that conflicting updates are likely.
The database acquires a lock before changes are made.

```sql
START TRANSACTION;

SELECT quantity
FROM inventory
WHERE product_id = 10
FOR UPDATE;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 10;

COMMIT;
```

`FOR UPDATE` asks supporting databases to lock selected rows for updating.

Pessimistic locking is useful when:

- A change must be made immediately
- Conflicts are expensive or likely
- The application has a short, predictable transaction

### Optimistic Locking

Optimistic locking assumes conflicts are uncommon.
It does not hold a long database lock while the application makes its decision.

The application tracks a version or timestamp:

```sql
UPDATE products
SET name = 'Mechanical Keyboard',
    version = version + 1
WHERE product_id = 42
  AND version = 7;
```

The application should check whether the update affected exactly one row.
If the affected row count is zero, another transaction changed the record first.
The application may reload the record and retry.

Optimistic locking is useful for:

- Short web requests
- Low-conflict workloads
- Systems that prefer avoiding long-held locks

---

## Intent Locks

An **intent lock** indicates that a transaction plans to acquire finer-grained locks lower in a lock hierarchy.

Examples:

- `intent shared` indicates an intention to acquire shared locks
- `intent exclusive` indicates an intention to acquire exclusive locks

Intent locks allow a database to coordinate table-level and row-level locking efficiently.
Application developers normally do not acquire intent locks directly.

## Isolation Levels

Isolation levels determine how transactions protect themselves from concurrent changes.

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read |
| --------------- | ---------- | ------------------- | ------------ |
| Read Uncommitted | Possible | Possible | Possible |
| Read Committed | Prevented | Possible | Possible |
| Repeatable Read | Prevented | Prevented | Usually prevented by MVCC, engine-dependent |
| Serializable | Prevented | Prevented | Prevented |

### Dirty Read

A **dirty read** occurs when a transaction reads uncommitted data from another transaction.

### Non-repeatable Read

A **non-repeatable read** occurs when a transaction reads the same row twice and sees a different value because another transaction committed a change.

### Phantom Read

A **phantom read** occurs when a repeated range query returns different sets of rows because another transaction inserted or deleted matching rows.

MySQL's InnoDB engine uses Repeatable Read as its default isolation level.
The SQL Standard uses a range of isolation guarantees, and implementations differ.

Set or check the level only when the database and application requirements are understood:

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

Supported syntax and session behavior vary by DBMS.

---

## MVCC

**Multiversion Concurrency Control (MVCC)** lets the database maintain multiple versions of rows.
A transaction reads an appropriate committed version rather than waiting for a writer to finish.

Benefits:

- Readers may not block writers.
- Writers may not block readers.
- Reads can remain consistent within a transaction.

Cost:

- Storage is needed for old versions.
- Cleanup processes must remove versions no longer needed.
- Long-running transactions can increase the amount of old-version data.

MVCC is a reason why one transaction can hold a row lock while another session successfully reads an older row version.

---

## Explicit Table Locks in MySQL

MySQL supports explicit table locks:

```sql
LOCK TABLES inventory READ;
```

This acquires a table read lock.

```sql
LOCK TABLES inventory WRITE;
```

This acquires a table write lock.

Always release explicit table locks:

```sql
UNLOCK TABLES;
```

Explicit table locking is usually unnecessary for InnoDB applications.
It can reduce concurrency and interfere with normal transaction behavior.
Prefer transaction and row-level controls.

MySQL table-lock syntax does not necessarily behave the same as Oracle, PostgreSQL, or SQL Server locking syntax.

---

## Lock Waiting

A lock wait occurs when a transaction asks for a lock that is already held by another transaction.

The database may:

- Let the transaction wait
- Time out after a configured interval
- Abort the transaction
- Deadlock-detect and cancel one transaction

Example with MySQL's InnoDB timeout setting:

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
```

The timeout is not usually the correct primary fix for lock problems.
First investigate why the lock is held for a long time.

---

## Deadlocks

A **deadlock** occurs when two or more transactions each hold a lock needed by another transaction.

### Example

**Transaction 1**

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 2;
```

**Transaction 2**

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 50
WHERE account_id = 2;

UPDATE accounts
SET balance = balance + 50
WHERE account_id = 1;
```

The first transaction may hold the lock on account `1` and need account `2`.
The second may hold account `2` and need account `1`.
Neither transaction can finish unless the database resolves the deadlock.

A database may choose one transaction as the victim and roll it back.
The application should handle that failure and retry safely.

---

## Preventing Deadlocks

Follow these practices:

1. **Access resources in the same order**

   - If code updates accounts `1`, then `2`, every transaction should use the same order.

2. **Keep transactions short**

   - Avoid external API calls, reports, and interactive input while a transaction is open.

3. **Update only the required rows**

   - Accurate `WHERE` clauses and indexes reduce lock ranges.

4. **Commit promptly**

   - Do not hold locks after all required work is complete.

5. **Use appropriate isolation**

   - Avoid unnecessarily restrictive levels.

6. **Handle deadlock errors and retry**

   - Retry only the transaction's complete logical unit.
   - Do not retry a transaction that has partially changed external systems.

7. **Use indexes**

   - Full scans and missing indexes can lock or scan far more rows than necessary.

---

## Finding Lock Problems in MySQL

Useful InnoDB status and metadata commands include:

```sql
SHOW ENGINE INNODB STATUS;
```

To inspect transaction and lock waits on recent MySQL versions:

```sql
SELECT *
FROM information_schema.innodb_trx;

SELECT *
FROM performance_schema.data_locks;

SELECT *
FROM performance_schema.data_lock_waits;
```

Availability and column names vary by MySQL version.

Look for:

- Transactions that have been open for a long time
- Repeated lock waits
- One session blocking multiple others
- Large row counts or long-running statements
- Deadlocks in InnoDB status output

On a production system, use a DBA or monitoring tool before killing processes.

---

## Blocking and Deadlocking Are Different

**Blocking** is normal and temporary:

- Transaction A holds a lock.
- Transaction B waits for it.
- Transaction A commits or rolls back.
- Transaction B continues.

**Deadlocking** is circular waiting:

- Transaction A waits for B.
- Transaction B waits for A.
- Neither can finish naturally.
- The database resolves it by rolling back a transaction or a database can time out a request.

## Locking in the Application

The application can use several strategies.

### 1. Keep the work in one transaction

Use transactions for dependent SQL statements:

```sql
START TRANSACTION;

UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 10;

INSERT INTO sales(product_id, quantity)
VALUES (10, 1);

COMMIT;
```

### 2. Check the affected row

For an optimistic update, verify the update result:

```sql
UPDATE accounts
SET balance = balance - 100,
    version = version + 1
WHERE account_id = 1
  AND version = 19;
```

If the row is not updated, reload the record and decide whether to retry.

### 3. Add a retry only for safe operations

Example logic:

```text
for up to 3 attempts:
    begin transaction
    perform database operations
    commit

    if deadlock:
        roll back
        retry

    if timeout or permanent error:
        roll back
        report the error
```

Do not automatically retry a non-idempotent external action.

## Laboratory Exercise: Observe a Row Lock

You need two MySQL sessions, labeled **Session A** and **Session B**.

Create the table:

```sql
CREATE TABLE lock_demo (
    item_id INT PRIMARY KEY,
    quantity INT NOT NULL
);

INSERT INTO lock_demo(item_id, quantity)
VALUES (1, 10);
```

### Session A

```sql
START TRANSACTION;

UPDATE lock_demo
SET quantity = quantity - 1
WHERE item_id = 1;

-- Do not commit yet
SELECT quantity FROM lock_demo WHERE item_id = 1;
```

### Session B

Try to update the same row:

```sql
UPDATE lock_demo
SET quantity = quantity - 1
WHERE item_id = 1;
```

Observe whether the statement waits or returns an error.

### Continue

In Session A:

```sql
COMMIT;
```

Session B will become able to finish only if it was permitted to proceed after waiting.

If Session A rolls back instead:

```sql
ROLLBACK;
```

The change in Session A is undone.

**Warning:** Do not leave a transaction open while moving between demonstrations.

## Laboratory Exercise: MVCC Read

Create a table and insert a row:

```sql
CREATE TABLE mvcc_demo (
    id INT PRIMARY KEY,
    value VARCHAR(50)
) ENGINE = InnoDB;

INSERT INTO mvcc_demo VALUES (1, 'Original');
COMMIT;
```

In Session A:

```sql
START TRANSACTION;
SELECT * FROM mvcc_demo WHERE id = 1;
```

In Session B:

```sql
START TRANSACTION;
UPDATE mvcc_demo
SET value = 'Changed'
WHERE id = 1;
COMMIT;
```

Observe Session A according to the configured isolation level.

In Repeatable Read, a plain read may continue to see the earlier consistent version in the same transaction.
A locking read may behave differently:

```sql
SELECT * FROM mvcc_demo
WHERE id = 1
FOR UPDATE;
```

Expected behavior varies with database engine and transaction state.

## Summary

| Concept | Description |
| ------- | ----------- |
| Lock | A control that restricts conflicting transaction operations |
| Shared lock | Allows reads while preventing conflicting writes |
| Exclusive lock | Prevents other conflicting access to a resource |
| Row lock | Protects a row or small set of rows |
| Table lock | Protects an entire table |
| Pessimistic locking | Acquires locks while the transaction is working |
| Optimistic locking | Checks a version or timestamp when writing |
| MVCC | Keeps row versions so readers and writers can coexist |
| Isolation level | Defines visible and conflicting transaction behavior |
| Blocking | One transaction waits for another lock |
| Deadlock | Two or more transactions wait in a circular dependency |

The goal is not to eliminate every lock.
The goal is to use the shortest, smallest, and most predictable locking strategy that supports correctness and required concurrency.
