# SQL Subqueries

## What Is a Subquery?

A **subquery** is a query nested inside another SQL statement. The inner query produces a value, a list of values, or a set of rows that the outer query can use.

Subqueries are useful when a result depends on another query, such as:

- Comparing a value with an average or maximum
- Finding rows related to a set of IDs
- Checking whether related rows exist
- Summarizing rows before joining or filtering them

The examples in this guide use the MySQL 8.0 `PersonalTrainer` database.

---

## A Basic Subquery

The following query finds Workouts whose maximum duration is greater than the average maximum duration for all Workouts:

```sql
SELECT
    w.`Name` WorkoutName,
    w.MaxMinutes
FROM Workout w
WHERE w.MaxMinutes > (
    SELECT AVG(w2.MaxMinutes)
    FROM Workout w2
);
```

The inner query returns one number. The outer query compares every Workout's `MaxMinutes` with that number.

The query can be read in two steps:

1. Calculate the average `MaxMinutes`.
2. Select Workouts whose `MaxMinutes` exceeds that average.

---

## Subquery Result Shapes

The shape of the inner query determines which operators are appropriate.

| Result Shape | Example | Common Use |
| ------------ | ------- | ---------- |
| One value | `SELECT AVG(MaxMinutes) ...` | Compare with `=`, `>`, `<`, or similar operators |
| One column with multiple values | `SELECT WorkoutId ...` | Compare with `IN` or `NOT IN` |
| One or more rows used as a table | `SELECT ... GROUP BY ...` | Join to it as a derived table |
| Existence test | `SELECT 1 ...` | Use with `EXISTS` or `NOT EXISTS` |

A scalar subquery used with a comparison must return one value. If it returns multiple rows, MySQL reports an error. An aggregate such as `AVG()` without `GROUP BY` normally returns one row, even when its input contains no rows; in that case, the value may be `NULL`.

---

## Scalar Subqueries

A **scalar subquery** returns one value. It can appear anywhere an expression is allowed, including a `WHERE` condition or the select list.

### Compare Against an Aggregate

This example finds ExerciseInstances with more Sets than the average for their Exercise:

```sql
SELECT
    e.`Name` ExerciseName,
    ei.ExerciseInstanceId,
    ei.Sets
FROM ExerciseInstance ei
INNER JOIN Exercise e ON ei.ExerciseId = e.ExerciseId
WHERE ei.Sets > (
    SELECT AVG(ei2.Sets)
    FROM ExerciseInstance ei2
    WHERE ei2.ExerciseId = ei.ExerciseId
)
ORDER BY e.`Name`, ei.ExerciseInstanceId;
```

The inner query returns one average for the ExerciseInstance's Exercise. The outer query compares the current instance with that average.

### Use a Scalar Subquery in the Select List

A scalar subquery can also add a value to each output row:

```sql
SELECT
    w.`Name` WorkoutName,
    w.MaxMinutes,
    (
        SELECT AVG(w2.MaxMinutes)
        FROM Workout w2
    ) AverageMaxMinutes
FROM Workout w;
```

The average is the same for every row. If the subquery depends on a value from the outer row, it is correlated.

## Multi-Row Subqueries: `IN`

Use `IN` when the inner query returns a list of values.

This query finds Workouts associated with the Goal named `Core Strength`:

```sql
SELECT
    w.WorkoutId,
    w.`Name` WorkoutName
FROM Workout w
WHERE w.WorkoutId IN (
    SELECT wg.WorkoutId
    FROM WorkoutGoal wg
    INNER JOIN Goal g ON wg.GoalId = g.GoalId
    WHERE g.`Name` = 'Core Strength'
)
ORDER BY w.`Name`;
```

The subquery returns the IDs of matching Workouts. The outer query returns their names and IDs.

`IN` is often a clear choice when asking whether a value matches any result from a subquery. It also avoids duplicating outer rows when multiple related rows match.

## Existence Tests: `EXISTS` and `NOT EXISTS`

`EXISTS` tests whether a subquery returns at least one row. The columns selected by the subquery are not used; a common convention is `SELECT 1`.

### Find Clients Who Have Goals

```sql
SELECT
    c.ClientId,
    c.FirstName,
    c.LastName
FROM Client c
WHERE EXISTS (
    SELECT 1
    FROM ClientGoal cg
    WHERE cg.ClientId = c.ClientId
)
ORDER BY c.LastName, c.FirstName;
```

For each Client, the correlated subquery looks for at least one matching `ClientGoal` row.

### Find Clients Who Have No Workouts

```sql
SELECT
    c.ClientId,
    c.FirstName,
    c.LastName
FROM Client c
WHERE NOT EXISTS (
    SELECT 1
    FROM ClientWorkout cw
    WHERE cw.ClientId = c.ClientId
)
ORDER BY c.LastName, c.FirstName;
```

This query returns Clients with no matching `ClientWorkout` row. In the exercise dataset, that result contains 50 Clients.

`NOT EXISTS` is usually a reliable way to express “there is no related row.” It does not have the same `NULL` trap that can affect `NOT IN`.

## Correlated and Non-Correlated Subqueries

A **non-correlated subquery** does not refer to a column from the outer query. It can be evaluated independently:

```sql
SELECT
    w.`Name`,
    w.MaxMinutes
FROM Workout w
WHERE w.MaxMinutes > (
    SELECT AVG(w2.MaxMinutes)
    FROM Workout w2
);
```

A **correlated subquery** refers to a value from its outer query. The database evaluates its result in relation to each outer row, although the optimizer may transform the query internally.

The ExerciseInstance average above is correlated because its inner query uses `ei.ExerciseId` from the outer query:

```sql
WHERE ei2.ExerciseId = ei.ExerciseId
```

Use clear aliases so it is easy to identify which query each column belongs to. Qualifying correlated references is especially important when the inner and outer queries use the same table.

---

## Derived Tables

A **derived table** is a subquery in the `FROM` clause. It produces rows that the outer query can treat like a table. MySQL requires a derived table to have an alias.

This query first calculates one total per Invoice, then compares each total to the average of all invoice totals:

```sql
SELECT
    totals.InvoiceId,
    totals.InvoiceTotal
FROM (
    SELECT
        li.InvoiceId,
        SUM(li.Price * li.Quantity) InvoiceTotal
    FROM InvoiceLineItem li
    GROUP BY li.InvoiceId
) totals
WHERE totals.InvoiceTotal > (
    SELECT AVG(invoice_totals.InvoiceTotal)
    FROM (
        SELECT SUM(li2.Price * li2.Quantity) InvoiceTotal
        FROM InvoiceLineItem li2
        GROUP BY li2.InvoiceId
    ) invoice_totals
)
ORDER BY totals.InvoiceTotal, totals.InvoiceId;
```

This compares an invoice's total with the **average invoice total**, not the average line-item amount. The grouping level matters: the inner aggregate must calculate one value per Invoice before the average is taken.

For a query with several named intermediate results, a CTE may be easier to read than nesting derived tables. See [Common Table Expressions](./2.2_Common_Table_Expressions.md).

## Subquery Versus Join

Some tasks can be written either with a subquery or a join. Choose based on the question and the result shape:

- Use `EXISTS` when the question is whether a related row exists and you do not need its columns.
- Use a join when you need columns from both tables.
- Use `IN` when a value must match a list returned by another query.
- Use a derived table when an intermediate result needs to be treated as a row source.

A join can return multiple copies of an outer row when several related rows match. `EXISTS` and `IN` express membership without multiplying those outer rows.

## Common Mistakes

### A Scalar Subquery Returns Multiple Rows

This comparison expects one value:

```sql
WHERE w.LevelId = (
    SELECT LevelId
    FROM Workout
);
```

If the subquery returns multiple rows, the comparison fails. Use `IN` if the intended operation is to compare against multiple values.

### `NOT IN` and `NULL`

If a `NOT IN` subquery can return `NULL`, the comparison may evaluate to unknown instead of true, causing rows to be filtered out unexpectedly.

For anti-matching queries, `NOT EXISTS` often makes the intended relationship clearer:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM ClientWorkout cw
    WHERE cw.ClientId = c.ClientId
)
```

### Comparing Values at Different Levels

Before writing nested aggregates, decide what each row represents. An average of line items is not the same as an average of invoice totals. Aggregate at the intended level first.

### Forgetting the Correlation Condition

Without a condition that connects the inner query to the outer row, a query intended to be correlated may instead compare every row against the same global result.

### Assuming a Subquery Always Runs Once Per Outer Row

SQL describes the result, not a required execution procedure. The optimizer may rewrite a subquery or use a different execution strategy. Use `EXPLAIN` to inspect a plan when performance matters.

## A Practical Workflow

When solving a problem with a subquery:

1. State the question in plain language.
2. Identify what the inner query should return: one value, a list, a set of rows, or an existence result.
3. Write and run the inner query independently.
4. Confirm its result shape and meaning.
5. Add the outer query and the appropriate operator.
6. Add correlation only when the inner result depends on the current outer row.
7. Check for duplicate rows, `NULL` values, and the intended aggregation level.
8. Use `EXPLAIN` if query performance needs investigation.

## Summary

| Technique | Purpose |
| --------- | ------- |
| Scalar subquery | Supplies one value to a comparison or expression |
| `IN` | Checks whether a value matches one of several returned values |
| `EXISTS` | Checks whether at least one related row exists |
| `NOT EXISTS` | Checks that no related row exists |
| Correlated subquery | Uses a value from the current outer row |
| Derived table | Uses subquery results as rows in the `FROM` clause |

Use the form that best expresses the relationship being tested. Verify the inner query's result shape first, and make the intended grouping and `NULL` behavior explicit.
