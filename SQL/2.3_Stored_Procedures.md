# MySQL Stored Procedures

## What Is a Stored Procedure?

A **stored procedure** is a named collection of SQL statements saved in a database. Applications or database users execute it with `CALL`.

Procedures are useful when a database task:

- Is called repeatedly
- Has multiple related SQL steps
- Needs a consistent interface for applications
- Should keep some data-access logic in the database

A procedure can accept parameters, run SQL statements, use local variables and conditional logic, and return result sets or values through `OUT` parameters.

The examples in this guide use MySQL 8.0 and the `PersonalTrainer` database.

---

## Creating and Calling a Procedure

```sql
DELIMITER //

CREATE PROCEDURE GetWorkoutsByLevel(
    IN p_LevelId INT
)
BEGIN
    SELECT
        WorkoutId,
        `Name` WorkoutName,
        MaxMinutes
    FROM Workout
    WHERE LevelId = p_LevelId
    ORDER BY `Name`;
END //

DELIMITER ;
```

Call the procedure with a LevelId:

```sql
CALL GetWorkoutsByLevel(1);
```

The procedure returns a result set because its body contains a `SELECT` that returns rows.

---

## Why Change the Delimiter?

SQL statements normally end with a semicolon. A procedure body contains multiple statements that also use semicolons. In MySQL command-line clients and common GUI tools, `DELIMITER` temporarily changes the statement terminator so the entire `CREATE PROCEDURE` definition can be sent together.

```sql
DELIMITER //
CREATE PROCEDURE ExampleProcedure()
BEGIN
    SELECT 'First statement';
    SELECT 'Second statement';
END //
DELIMITER ;
```

`DELIMITER` is a client command; it is not part of the stored procedure and is not sent to the MySQL server as SQL. Use the delimiter syntax supported by the tool where you run the script.

## Procedure Parameters

### `IN`

An `IN` parameter supplies a value to the procedure. It is the default parameter mode, but writing `IN` makes the intent clear.

```sql
IN p_LevelId INT
```

Use the parameter in SQL statements in the procedure body:

```sql
WHERE LevelId = p_LevelId
```

### `OUT`

An `OUT` parameter carries a value from the procedure back to its caller. In MySQL, pass a user-defined variable when calling a procedure with an `OUT` parameter:

```sql
DELIMITER //

CREATE PROCEDURE GetInvoiceTotal(
    IN p_InvoiceId INT,
    OUT p_InvoiceTotal DECIMAL(30, 8)
)
BEGIN
    SELECT COALESCE(SUM(Price * Quantity), 0)
    INTO p_InvoiceTotal
    FROM InvoiceLineItem
    WHERE InvoiceId = p_InvoiceId;
END //

DELIMITER ;
```

Call it and read the output:

```sql
SET @invoice_total = 0;
CALL GetInvoiceTotal(1, @invoice_total);
SELECT @invoice_total InvoiceTotal;
```

`SELECT ... INTO` stores a query result in a local or output variable. An aggregate query without `GROUP BY` returns one row; `COALESCE()` makes the result zero if the invoice has no line items.

### `INOUT`

An `INOUT` parameter supplies an initial value and returns its updated value:

```sql
DELIMITER //

CREATE PROCEDURE AddToCounter(
    IN p_increment INT,
    INOUT p_counter INT
)
BEGIN
    SET p_counter = p_counter + p_increment;
END //

DELIMITER ;
```

```sql
SET @counter = 10;
CALL AddToCounter(3, @counter);
SELECT @counter;
```

The final value is `13`.

## Local Variables and Control Flow

Declare local variables at the beginning of a `BEGIN ... END` block, before executable statements:

```sql
DECLARE v_invoice_count INT DEFAULT 0;
```

Assign values with `SET` or `SELECT ... INTO`. Use `IF`, `CASE`, or loops when the procedure needs conditional or repeated work.

```sql
IF p_InvoiceId <= 0 THEN
    SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'InvoiceId must be positive';
END IF;
```

`SIGNAL` raises a condition and stops normal execution of the current procedure path. `SQLSTATE '45000'` is commonly used for a user-defined exception.

---

## Returning Rows and Returning Values

A procedure can return a result set by executing a `SELECT`:

```sql
CALL GetWorkoutsByLevel(1);
```

It can also return scalar values with `OUT` parameters. Choose the form that fits the caller:

- Return rows when the caller needs a set of records.
- Use `OUT` parameters for one or more output values.
- Use both when the procedure needs to return detailed rows and summary values.

MySQL procedures do not use a `RETURN` statement to return a scalar value in the same way a stored function does. Do not confuse procedures and functions: a function is designed to return a value as part of an expression.

---

## Error Handling

Stored programs can declare handlers for conditions such as SQL exceptions or missing rows. A handler's scope is the `BEGIN ... END` block where it is declared.

```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    ROLLBACK;
    RESIGNAL;
END;
```

Use transaction handlers only when the procedure owns the transaction. A procedure that runs inside a transaction started by its caller should not unexpectedly commit or roll back the caller's work.

For a simple validation rule, `SIGNAL` can report a clear error without adding a handler:

```sql
IF p_InvoiceId IS NULL OR p_InvoiceId <= 0 THEN
    SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'A positive InvoiceId is required';
END IF;
```

## Managing Stored Procedures

List procedures in the current database:

```sql
SHOW PROCEDURE STATUS
WHERE Db = 'PersonalTrainer';
```

Inspect a procedure definition:

```sql
SHOW CREATE PROCEDURE GetWorkoutsByLevel;
```

Remove a procedure by its exact name:

```sql
DROP PROCEDURE IF EXISTS GetWorkoutsByLevel;
```

MySQL does not support `CREATE OR REPLACE PROCEDURE` in the same way it supports that syntax for some other object types. A common development workflow is to drop and recreate the named procedure. Take care not to drop a procedure used by an application or another developer.

---

## Security and Design Considerations

- Grant only the permissions required to create or execute procedures.
- Use parameterized procedure calls from applications; do not build SQL by concatenating untrusted text.
- Decide whether the procedure should execute with the definer's privileges or the caller's privileges. Review `SQL SECURITY DEFINER` and `SQL SECURITY INVOKER` before changing defaults.
- Keep each procedure focused and use descriptive names for parameters and local variables.
- Avoid hiding important side effects. Document data changes and transaction behavior.
- Keep transactions short. Coordinate transaction ownership between the procedure and its caller.
- Use procedures for reusable database operations, not as a substitute for clear table design or application architecture.

## Common Mistakes

### Forgetting `DELIMITER`

The client may treat the first semicolon in a procedure body as the end of the `CREATE PROCEDURE` statement. Change the delimiter while defining the procedure, then restore it.

### Confusing Procedure Parameters with User Variables

Procedure parameters have names such as `p_InvoiceId`. User variables such as `@invoice_total` exist in the client session and are often used to receive `OUT` values.

### Declaring Variables After Statements

In a compound block, declare local variables and handlers before executable statements.

### Returning No Value from an `OUT` Parameter

An `OUT` parameter must be assigned along every successful execution path where its value is expected.

### Swallowing Errors

Do not catch an error and return a success-shaped value unless that is an intentional, documented behavior. Prefer a clear error or re-signal the original exception.

---

## A Practical Workflow

1. Define the procedure's input and output contract.
2. Write and test the core `SELECT` or DML statement independently.
3. Add parameters and qualify table columns with aliases.
4. Add control flow or error handling only when needed.
5. Create or recreate the procedure using the delimiter syntax supported by the client.
6. Call it with representative values, including boundary and invalid cases.
7. Inspect its definition with `SHOW CREATE PROCEDURE`.
8. Confirm privileges, transaction behavior, and side effects before application use.

## Summary

| Feature | Purpose |
| ------- | ------- |
| `CALL` | Execute a stored procedure |
| `IN` | Pass a value into a procedure |
| `OUT` | Return a value to the caller |
| `INOUT` | Pass a value in and return its updated value |
| `SELECT ... INTO` | Store a query result in a variable |
| `IF` / `CASE` | Implement conditional behavior |
| `SIGNAL` | Raise a user-defined error condition |
| `SHOW CREATE PROCEDURE` | Inspect a procedure definition |

Stored procedures provide a reusable database interface. Make their parameters, results, errors, permissions, and transaction behavior explicit.
