# Best-Practice Troubleshooting Steps for Production Support, SRE, and DevOps

While the responsibilities of Production Support, SRE, and DevOps professionals differ, the most effective engineers follow a structured troubleshooting methodology. The goal is to:

- Restore service quickly
- Minimize business impact
- Identify the root cause
- Prevent future occurrences

---

# Universal Troubleshooting Process

## 1. Identify the Problem

Start by clearly understanding the issue.

### Questions to Ask

```text
What is broken?
Who is affected?
When did the issue begin?
Is it intermittent or constant?
Has it worked before?
What changed recently?
```

### Example

```text
Users cannot access the payroll application.

Started at 9:15 AM.

Only production is affected.

A deployment occurred at 9:00 AM.
```

---

## 2. Assess Impact and Severity

Determine the business impact and assign a priority.

### Severity Levels

| Severity | Description |
|-----------|-------------|
| P1 | Complete outage |
| P2 | Major functionality unavailable |
| P3 | Partial degradation |
| P4 | Minor issue |

### Example

```text
Database unavailable.
All users impacted.
Revenue-generating application down.

Severity: P1
```

---

## 3. Verify the Issue

Confirm that the issue actually exists and gather evidence.

### Validation Areas

- Monitoring alerts
- Error messages
- Application logs
- Customer reports
- System dashboards

### Example

```text
User reports login failures.

Verify:
- Reproduce the issue
- Check authentication logs
- Review monitoring alerts
```

---

## 4. Troubleshoot Using the OSI Model

Work through the stack logically.

### Layer 1: Physical

Verify:

```text
Server powered on
Cable connected
VM running
Hypervisor healthy
```

---

### Layer 2: Data Link

Verify:

```text
Switch port status
VLAN assignments
MAC address learning
```

---

### Layer 3: Network

Verify:

```text
IP address
Subnet mask
Default gateway
Routing
```

Commands:

```bash
ping
tracert
traceroute
```

---

### Layer 4: Transport

Verify:

```text
Required ports open
Firewall access
Load balancer configuration
```

Commands:

```bash
telnet hostname port
Test-NetConnection
netstat
```

---

### Layer 7: Application

Verify:

```text
Application service status
Database connectivity
Application health checks
API responses
```

# Production Support Troubleshooting Process

Production Support teams focus on restoring service as quickly as possible.

## Step 1: Review Monitoring Tools

Examples:

```text
Splunk
Dynatrace
AppDynamics
Datadog
CloudWatch
Azure Monitor
```

Look for:

```text
CPU spikes
Memory issues
Increased latency
High error rates
Service failures
```

---

## Step 2: Examine Logs

Review:

```text
Application logs
Server logs
Database logs
Web server logs
```

Common Indicators:

```text
Exceptions
Timeouts
Authentication failures
Connection errors
```

Example:

```text
Application cannot connect to SQL database.
Connection timeout found in logs.
```

---

## Step 3: Check Dependencies

Many outages originate from dependent systems.

Verify:

```text
Databases
APIs
DNS
Message queues
LDAP/Active Directory
Third-party services
```

Example:

```text
Application healthy.

Database offline.

Root cause:
Database outage.
```

---

## Step 4: Investigate Recent Changes

Determine whether something changed before the incident.

Verify:

```text
Deployments
Configuration changes
Patch installations
Infrastructure changes
Certificate renewals
```

A recent change is often the source of production incidents.

---

## Step 5: Mitigate Quickly

Possible mitigation actions:

```text
Restart service
Rollback deployment
Scale infrastructure
Fail over to backup systems
Redirect traffic
```

### Goal

```text
Restore service first.
Investigate root cause second.
```

---

# SRE Troubleshooting Methodology

Site Reliability Engineers focus on reliability, performance, and resilience.

---

## Step 1: Evaluate SLIs and SLOs

Examples:

```text
Availability
Latency
Error Rate
Throughput
```

Questions:

```text
Are service-level objectives being violated?
How severe is the degradation?
```

---

## Step 2: Examine the Four Golden Signals

### Latency

```text
Requests taking too long
```

### Traffic

```text
Unexpected increase or decrease in request volume
```

### Errors

```text
HTTP 500 responses
Application exceptions
Failed transactions
```

### Saturation

```text
CPU utilization
Memory usage
Disk utilization
Connection exhaustion
```

---

## Step 3: Correlate Events

Create a timeline of events.

Review:

```text
Deployments
Infrastructure changes
Configuration updates
Traffic spikes
Cloud incidents
```

Timeline analysis frequently reveals the triggering event.

---

## Step 4: Verify Platform Health

Review:

```text
Servers
Containers
Pods
Load balancers
Kubernetes clusters
Databases
```

Commands:

```bash
kubectl get pods
kubectl describe pod
kubectl logs
kubectl get events
```

---

## Step 5: Perform Root Cause Analysis (RCA)

Ask:

```text
Why did the incident happen?
Why wasn't it detected earlier?
Why wasn't it prevented?
```

Common RCA Techniques:

```text
5 Whys
Fishbone Diagram
Blameless Postmortem
```

---

# DevOps Troubleshooting Process

DevOps engineers frequently troubleshoot CI/CD pipelines, deployments, and infrastructure automation.

---

## Step 1: Verify Pipeline Status

Review:

```text
Azure DevOps
GitHub Actions
Jenkins
GitLab CI/CD
```

Questions:

```text
Did the build succeed?
Did deployment complete?
Were tests successful?
```

---

## Step 2: Validate Artifacts

Ensure the correct artifact was deployed.

Verify:

```text
Build version
Container image
Application package
Release tag
```

Example:

```text
Version 2.4 deployed accidentally instead of 2.5.
```

---

## Step 3: Review Deployment Logs

Review:

```text
Build logs
Pipeline logs
Deployment logs
Application startup logs
```

Look for:

```text
Configuration failures
Missing dependencies
Permission issues
Secret retrieval failures
```

---

## Step 4: Verify Configuration

Review:

```text
Environment variables
Secrets
Connection strings
Certificates
Feature flags
DNS entries
```

Many deployment failures are configuration-related.

---

## Step 5: Validate Infrastructure

Verify:

```text
Virtual Machines
Containers
Storage accounts
Kubernetes clusters
Networking
IAM permissions
```

Example:

```text
Deployment successful.

Application cannot access storage account.

Root cause:
Insufficient permissions.
```

# Interview-Friendly Troubleshooting Framework

A simple framework that works well for Production Support, SRE, and DevOps interviews:

```text
1. Identify the problem
2. Assess business impact
3. Gather evidence
4. Review monitoring and alerts
5. Check logs
6. Verify infrastructure health
7. Verify network connectivity
8. Check dependencies
9. Review recent changes
10. Implement mitigation
11. Perform root cause analysis
12. Document findings
13. Implement preventive measures
```

---

## Example Interview Answer

**Question:** "An application is down. How would you troubleshoot it?"

### Step 1: Identify the Problem

```text
Understand the symptoms.
Determine who is affected.
Determine when the issue started.
```

### Step 2: Assess Impact

```text
Is this a P1 outage?
How many users are affected?
What business functions are impacted?
```

### Step 3: Gather Evidence

```text
Review monitoring dashboards.
Examine alerts.
Collect error messages.
```

### Step 4: Check Logs

```text
Application logs
Web server logs
Database logs
System logs
```

### Step 5: Verify Infrastructure Health

```text
CPU utilization
Memory utilization
Disk space
Server availability
Container health
```

### Step 6: Verify Network Connectivity

```text
Ping
Traceroute
DNS resolution
Firewall connectivity
Port accessibility
```

### Step 7: Check Dependencies

```text
Database availability
API availability
Message queues
Authentication services
DNS services
```

### Step 8: Review Recent Changes

```text
Deployments
Configuration changes
Patches
Certificate renewals
Infrastructure updates
```

### Step 9: Implement Mitigation

```text
Rollback deployment
Restart service
Scale resources
Fail over to secondary systems
```

### Step 10: Perform Root Cause Analysis

```text
Why did the issue occur?
What allowed it to occur?
What controls were missing?
```

### Step 11: Document Findings

```text
Timeline
Root cause
Mitigation steps
Lessons learned
```

### Step 12: Prevent Recurrence

```text
Improve monitoring
Add automation
Update runbooks
Implement alerts
Strengthen testing
```

# Senior-Level Troubleshooting Mindset

A strong Production Support, SRE, or DevOps engineer follows this approach:

```text
Observe
↓
Hypothesize
↓
Test
↓
Verify
↓
Mitigate
↓
Root Cause Analysis
↓
Prevention
```

Avoid:

```text
Guessing
Making assumptions
Changing multiple things at once
Skipping documentation
```

Instead:

```text
Collect facts
Change one variable at a time
Verify each step
Document everything
```

# The 30-Second Interview Answer

If you're asked this in an interview, a concise answer is:

> "I begin by identifying the problem and assessing the impact. I review monitoring dashboards, alerts, and logs to gather evidence. Next, I verify infrastructure health, network connectivity, and dependent systems such as databases and APIs. I review recent changes, including deployments and configuration updates, to identify potential causes. My first priority is restoring service through mitigation actions if needed. Once the issue is resolved, I perform a root cause analysis, document the findings, and implement preventive measures to avoid future incidents."
